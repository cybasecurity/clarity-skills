# Recall corrections

Models often recall these rules wrong. Check the target language, epoch and deployed dependencies before applying one. Most entries end with the sources to verify or cite.

- **M01 Recursion tracks functions, not contracts:** The VM tracks contract-qualified function IDs: `router.start → lender.lend → router.callback` can execute; reentering active `lender.lend` aborts. Other lender functions can observe intermediate state, so review reachable entry points and invariants. Sources: pinned stacks-core `clarity/src/vm/mod.rs::check_call_preconditions`, `callables.rs::DefinedFunction`, `contexts.rs::CallStack`.
- **M02 Native FT/NFT primitives do not authenticate owners:** They check ownership/balances and asset validity; wrappers authorize callers, and applications define mint/burn roles. Native `stx-transfer?` checks its sender against the effective `tx-sender`, which contract origin scopes change. Trace wallet → router → token separately from wallet → token. Source: `clarity/src/vm/functions/assets.rs`.
- **M03 `is-standard` checks network address versions:** It compares the principal's address version with the execution network; matching contract principals return `true`. It proves neither wallet/EOA identity, trust, nor key control; use it only where this network predicate is required. Clarity 1's separate `principal-of?` testnet derivation bug persists in old contracts; distinguish these functions. Source: `functions/principals.rs::special_is_standard`.
- **M04 Name current time exactly:** Use `stacks-block-time` in Clarity 4+. Previous-block time is historical; current-block info lookup returns `none`. Miner-set timestamps obey consensus constraints, not exact wall time. Source: [version-specific behavior](../../clarity-epochs/SKILL.md#version-specific-behavior).
- **M05 `as-contract?` semantics:** Clarity 4 introduces it and removes legacy `as-contract` from that version. No body expression may be response-typed. Outer-context allowances are evaluated before execution; cumulative outflows are checked at scope exit; violations roll back the scope and return errors. Handle the outer response; capture actors before switching context. Clarity 6 replaces `with-stacking` with `with-staking` and adds `with-pox` (no amount) for `unstake`-type calls; epoch 3.4 sums STX transfers/burns against `with-stx`. Sources: VM `functions/assets.rs`, the analyzer, SIP-033/039/044/045.
- **M06 Errors and rollback have boundaries:** The analyzer rejects unchecked intermediate responses in `begin`; `let` bindings and `map` lists can still hide errors. A private `err` alone does not revert writes. A nested public `err` reverts its callee scope; a handling caller returning `ok` can commit its own changes. Reverted prints are discarded. Test responses and committed balances, state and events. Source: [semantics every skill relies on](../../clarity-epochs/SKILL.md#semantics-every-skill-relies-on).
- **M07 Separate size and depth limits:** Stack depth, value size, serialization bounds and deployment size are distinct ([resource limits](../../clarity-epochs/SKILL.md#resource-limits); source: `clarity-types/src/{lib.rs,types/mod.rs}`).
- **M08 Epoch changes affect old contracts:** Epoch 3.4 disables `at-block` even for existing Clarity 1–4; Clarity 4's `secp256r1-verify` double hash persists while newer contracts use the prehash. Resolve function, version and epoch gates; do not claim upgrades universally changed `tx-sender`. Repository HEAD, proposal status, deployed version and simulator support are distinct evidence. Source: [version-specific behavior](../../clarity-epochs/SKILL.md#version-specific-behavior).
- **M09 Five execution dimensions; other limits are separate:** Runtime, read count/length, write count/length; memory, source size and stack depth are separate constraints. Refresh `/v2/pox` (`epochs[].block_limit`; [resource limits](../../clarity-epochs/SKILL.md#resource-limits)): SDK 3.26.0 reports older read limits, and the 25%-of-remaining block soft limit is configurable miner policy.
- **M10 SIP-006 covers costs; voting is disabled:** SIP-002 covers language foundations; SIP-006 covers cost assessment and voting. SIP-044 disables voting at epoch 4.0, which selects native Rust costs_5; earlier epochs require their own dispatch. Filenames do not prove activation: inspect `costs/mod.rs`, numbered schedules, delegated formulas and charge sites, and measure full realistic transactions.
- **M11 sBTC ownership differs from spendable balance:** Use `get-balance-available` for liquidity and `get-balance-locked` for pending withdrawals; `get-balance` sums both, so it overstates what can be transferred or repaid now. Check the available balance before any immediate Stacks transfer or repayment, not only before a Bitcoin redemption. Source: [sbtc-token.clar](https://github.com/stacks-sbtc/sbtc/blob/eb507946c65bdf4dde72469ea8cb2481fa276a17/contracts/contracts/sbtc-token.clar).
- **M12 Compose actual roles and payloads:** Before generating a protocol call, read the deployed source and the selected [protocol recipe](../../clarity-protocols/SKILL.md). Identify who must be the payer, caller, initiator, callback and receiver, whether the operation is synchronous or queued, and which payload format the runtime parser expects. For flash loans, confirm the eligibility rule and the callback name on the deployed contract. Recalled addresses and callback names are not evidence: refresh them from chain state.
- **M13 Hash chain identifiers in the correct order:** `index_block_id = SHA512/256(block_hash_bytes || consensus_hash_bytes)`; the argument order of the `StacksBlockId::new` constructor differs from the hashed order. Use SHA-512/256, not a manually truncated SHA-512. Pin source and ABI reads to one supported tip and verify the canonical deployment separately. Source: `StacksBlockId::new` in [chainstate.rs](https://github.com/stacks-network/stacks-core/blob/ccf31dc69cddb9a7125e286e733b24484b073133/stacks-common/src/types/chainstate.rs).
- **M14 Separate SIP clauses from security design:** SIP-009 specifies transfer ownership outcomes, not caller authentication; the implementation must authorize the sender. SIP-010 gives an example sender check, and its `u1`–`u4` transfer errors use "should": classify a deviation at the clause's normative strength. Print a present memo unwrapped after a successful transfer; `some 0x` differs from `none`. A matching trait does not prove semantic compliance. Source: normative SIP-009 and SIP-010 text.
- **M15 Verify incident causes:** Before attributing an incident, confirm the public report URL, the affected commit, the deployed source at the principal, the transaction and the remediation status. Keep distinct causes apart: a trait or proposal-role flaw, a source-attestation problem (reviewed code never successfully deployed at the principal), and unrelated incidents on the same protocol. Source in a transaction proves nothing unless that deployment succeeded; check the transaction result.
