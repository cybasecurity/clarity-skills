# Upgrade source examples

Protocol sources that separate stable state from replaceable logic, and concrete migrations. The rules they illustrate are in [clarity:upgrades](../SKILL.md).

## Source examples

How Zest v2, Hermetica hBTC, Stacking DAO and Zest v1 separate stable state from replaceable logic. Read only the relevant example; copy the separation of responsibilities, not its entire authorization policy.

| Pattern | Source | Implication |
|---|---|---|
| Stable collateral/debt store, replaceable market | Zest v2 [market-vault](https://github.com/Zest-Protocol/zest-v2-contracts/blob/f2fce52672bf5bca2c082a132b7ea6edd769b324/mainnet/contracts/market/v0-market-vault.clar) stores obligation registry, reverse index, collateral and scaled debt; `set-impl` changes the immediate caller allowed to mutate them. | Replacing market logic need not move these records or collateral. Lending vaults and other dependencies still need their own permission/compatibility review. |
| Stable SIP-010 token, replaceable minter | Zest v2 [zvstBTC](https://github.com/Zest-Protocol/zest-v2-contracts/blob/f2fce52672bf5bca2c082a132b7ea6edd769b324/mainnet/contracts/strategy-vault/zvstBTC.clar#L35-L55) keeps SIP-010 `transfer` and gates `mint` and `burn` to `authorized-minter`, which [zv-state](https://github.com/Zest-Protocol/zest-v2-contracts/blob/f2fce52672bf5bca2c082a132b7ea6edd769b324/mainnet/contracts/strategy-vault/zv-state-stbtc-0.clar#L356-L370) switches with the engine after a timelocked request. | The layout for an open token: wallets, allowances and integrators keep naming zvstBTC while the engine changes. |
| Separate reserve, state, token and controllers | Hermetica hBTC [reserve](https://github.com/hermetica-fi/hermetica-contracts/blob/5e13e431f69dd840fe297791fa2a73d9993a27e0/mainnet/contracts/hbtc/protocol/reserve-v1.clar), [state](https://github.com/hermetica-fi/hermetica-contracts/blob/5e13e431f69dd840fe297791fa2a73d9993a27e0/mainnet/contracts/hbtc/protocol/state-v1.clar) and [token](https://github.com/hermetica-fi/hermetica-contracts/blob/5e13e431f69dd840fe297791fa2a73d9993a27e0/mainnet/contracts/hbtc/tokens/token-hbtc.clar) consult HQ roles. | New modules can use the existing core if authorized; transfer recipients/assets and mint powers require separate checks. HQ grants/removals use [staged administration](../../governance/references/protocol-examples.md#hermetica-hbtc-example). |
| Shared protocol registry | Stacking DAO [DAO registry](https://github.com/StackingDAO/stackingdao-smart-contracts/blob/125c73dc109988730156f4d0434ff01654480fc7/mainnet/contracts/dao/dao.clar), [token](https://github.com/StackingDAO/stackingdao-smart-contracts/blob/125c73dc109988730156f4d0434ff01654480fc7/mainnet/contracts/tokens/ststx-token.clar) and [reserve](https://github.com/StackingDAO/stackingdao-smart-contracts/blob/125c73dc109988730156f4d0434ff01654480fc7/mainnet/contracts/reserves/stx-reserve-v2.clar). | Registry roles connect product logic to stable contracts. Broad protocol membership may grant several powers; review the complete role graph. |
| Stable token ledger behind a logic facade | Zest v1 [zststx](https://github.com/Zest-Protocol/zest-contracts/blob/3564bc38906e464ec4de774122bb9bbaee20ddc6/onchain/contracts/borrow/production/ztoken/zststx.clar#L70-L80), deployed as `zststx-v2-0`, forwards transfer, mint and burn to [zststx-token](https://github.com/Zest-Protocol/zest-contracts/blob/3564bc38906e464ec4de774122bb9bbaee20ddc6/onchain/contracts/borrow/production/ztoken/zststx-token.clar#L52-L71), which admits only approved callers. | Fits a token only protocol contracts move. Allowances and post-conditions name the [defined token](https://github.com/Zest-Protocol/zest-contracts/blob/3564bc38906e464ec4de774122bb9bbaee20ddc6/onchain/contracts/borrow/production/ztoken/zststx-token.clar#L10) `zststx-token::zststx` in principal units, not the facade's interest-adjusted balance. Preserve the index/rounding relationship and the ledger's authorized callers. |

### Concrete migration sources

- Bitflow DLMM [migrate-pool / accept-migrated-pool](https://github.com/BitflowFinance/bitflow-dlmm/blob/b4d3694c863fb737574b2830acaa33a02f399bc0/clarity/contracts/dlmm-core-v-1-1.clar#L324-L440): checks zero pending protocol fees and the approved target; imports pool identity, status, fee records and token direction into an authorized destination; advances the ID counter by maximum; changes the pool's core in the same call. Also review destination bin configuration, routers, new-pool templates and old entrypoint retirement. This source is a pattern, not proof that every related migration is complete.
- Stacking DAO [stSTXbtc migration](https://github.com/StackingDAO/contracts/blob/a8d7d2a2dcffa0b4759bc8411f9d1369fc44b736/contracts/version-3/ststxbtc-migration-v1.clar): protocol-authorized batches or self-migration burn the old token and mint v2. The batch returns `(ok (map ...))` with per-address responses: a holder whose mint fails after its burn loses the balance while the batch succeeds, so inspect each result. Contract holders of the old token may be unable to transfer or redeem the new one; see the [public upgrade review](https://clarity-alliance.github.io/audits/Clarity%20Alliance%20-%20Stacking%20DAO%20%28Upgrade%29.pdf).
- Zest v1 stSTX z-tokens, a [version chain](migration.md#version-chain) and then a cut: each later version's `get-principal-balance` adds its predecessor's ([v2](https://github.com/Zest-Protocol/zest-contracts/blob/3564bc38906e464ec4de774122bb9bbaee20ddc6/onchain/contracts/borrow/legacy/v1/token/zststx.clar#L56-L63), [v3](https://github.com/Zest-Protocol/zest-contracts/blob/3564bc38906e464ec4de774122bb9bbaee20ddc6/onchain/contracts/borrow/legacy/v1-2/token/zststx.clar#L136-L143)), and v3 [moves an old balance](https://github.com/Zest-Protocol/zest-contracts/blob/3564bc38906e464ec4de774122bb9bbaee20ddc6/onchain/contracts/borrow/legacy/v1-2/token/zststx.clar#L218-L247) when the pool calls `cumulate-balance`. The user index lives in [pool-reserve-data](https://github.com/Zest-Protocol/zest-contracts/blob/3564bc38906e464ec4de774122bb9bbaee20ddc6/onchain/contracts/borrow/production/reserve-data/pool-reserve-data.clar#L221-L229), so moved principal keeps its interest. The repository's test-suite simulations [rewire approvals](https://github.com/Zest-Protocol/zest-contracts/blob/3564bc38906e464ec4de774122bb9bbaee20ddc6/onchain/contracts/borrow/production/mocks/migrate-v1-v2.clar#L109-L123) at each upgrade, then [burn and mint](https://github.com/Zest-Protocol/zest-contracts/blob/3564bc38906e464ec4de774122bb9bbaee20ddc6/onchain/contracts/borrow/production/mocks/migrate-v2-v3.clar#L351-L384) a [hard-coded holder list](https://github.com/Zest-Protocol/zest-contracts/blob/3564bc38906e464ec4de774122bb9bbaee20ddc6/onchain/contracts/borrow/production/mocks/migrate-v2-v3.clar#L234-L235) into the state contract and [rewrite](https://github.com/Zest-Protocol/zest-contracts/blob/3564bc38906e464ec4de774122bb9bbaee20ddc6/onchain/contracts/borrow/production/mocks/migrate-v2-v3.clar#L237-L279) saved burn heights as Stacks heights. The mainnet runs are on chain under `SP2VCQJGH7PHP2DJK7Z0V48AGBHQAW3R3ZW1QF4N`, not in the repository.
- Zest v1 mainnet cut, from 2024-12-17: after publishing the ledger `zststx-token` and its logic contract `zststx-v2-0`, the deployer published one-shot batch contracts [`ststx-t-part-1`](https://explorer.hiro.so/txid/SP2VCQJGH7PHP2DJK7Z0V48AGBHQAW3R3ZW1QF4N.ststx-t-part-1?chain=mainnet) to [`ststx-t-part-37`](https://explorer.hiro.so/txid/SP2VCQJGH7PHP2DJK7Z0V48AGBHQAW3R3ZW1QF4N.ststx-t-part-37?chain=mainnet), each with up to 200 hard-coded holders. Each `burn-mint-zststx` call checks the deployer as `tx-sender`, approves the batch on the four z-token versions, burns each holder's oldest non-empty old balance, mints it on `zststx-v2-0` and revokes the approvals; `fold` with `try!` makes the batch all-or-nothing. Sixteen 200-holder batches were never called; batches of about 10 holders named `ststx-t-part-N-M` ran instead.
- Zest v1 mainnet stSTXbtc migration, 2025-07-03: each contract was published first and then called in order. [`migrate-ststxbtc-v2`](https://explorer.hiro.so/txid/SP2VCQJGH7PHP2DJK7Z0V48AGBHQAW3R3ZW1QF4N.migrate-ststxbtc-v2?chain=mainnet) froze every reserve, moved the stSTXbtc reserve to the v2 stSTXbtc token and a new z-token, and rewired approvals. [`migrate-token-1`](https://explorer.hiro.so/txid/SP2VCQJGH7PHP2DJK7Z0V48AGBHQAW3R3ZW1QF4N.migrate-token-1?chain=mainnet) to `migrate-token-28` ran short hard-coded holder lists, skipping zero balances: per holder they re-keyed the per-asset records, burned the live old z-token balance and minted it on the new one. [`unpause`](https://explorer.hiro.so/txid/SP2VCQJGH7PHP2DJK7Z0V48AGBHQAW3R3ZW1QF4N.unpause?chain=mainnet) unfroze the reserves.
